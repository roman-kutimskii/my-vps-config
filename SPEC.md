# SPEC: Minimal VPS Setup for Remote Development

## Goal

Сделать минимальный и понятный Ansible-проект для первичной настройки нового VPS под удалённую разработку.

Проект предназначен только для личного использования.

Главный сценарий:

- купить новый VPS
- заполнить конфиг
- выполнить playbook-и
- получить готовую среду для работы без ручной системной настройки

## Scope

Что должно получиться после настройки:

- SSH-доступ как `dev` по ключу
- работающий `sudo` для `dev`
- Docker для Dev Containers и обычных контейнерных задач
- OpenCode, доступный в браузере по HTTPS на `opencode.example.com`
- базовый firewall
- каталог `/home/dev/projects` как удобное место для проектов

## Non-Goals

Проект не должен пытаться быть:

- универсальным для нескольких серверов
- переносимым между провайдерами
- системой долгосрочного управления конфигурацией
- сложным security/hardening проектом
- платформой для мониторинга, бэкапов и CI
- generic self-hosting framework

Это bootstrap-проект для одного чистого VPS.

## Target Environment

- провайдер: QWINS
- один VPS
- Ubuntu 24.04 LTS
- первый вход: `root` + пароль по SSH
- аварийный доступ через VNC остаётся вне scope проекта

## Main Workflow

Настройка может быть разбита на несколько простых playbook-ов, если так понятнее.

Минимально нужны два логических этапа:

1. bootstrap: подготовить сервер для нормальной работы через пользователя `dev`
2. final setup: поставить базовые компоненты и OpenCode

Допустимо оставить это как:

- `bootstrap.yml` и `site.yml`
- или `bootstrap.yml`, `base.yml`, `web.yml`

Главное требование: структура должна оставаться маленькой и понятной.

## Users and Access

Нужны два пользователя:

- `root` только для первого входа и аварийного доступа
- `dev` как основной рабочий пользователь

Требования:

- `dev` создаётся Ansible-ем
- SSH-ключ для `dev` берётся из конфига
- после bootstrap SSH password auth отключается
- после bootstrap прямой SSH-вход под `root` отключается
- дальнейшая работа по SSH идёт через `dev`

## Sudo

Для `dev` нужен `sudo`.

Требования:

- `sudo` требует пароль
- пароль `dev` хранится в `ansible-vault`
- последующие playbook-и могут использовать этот пароль для privilege escalation

## SSH Requirements

Достаточно следующего поведения:

- SSH работает на стандартном порту `22`
- вход по паролю после bootstrap отключён
- вход по SSH под `root` после bootstrap отключён
- SSH port forwarding должен продолжать работать для VS Code Remote SSH

Не нужно добавлять сложные ограничения и дополнительные hardening-настройки, если они не требуются для основного сценария.

## Network Model

Host firewall должен открывать только:

- `22/tcp`
- `80/tcp`
- `443/tcp`

Временные dev-сервисы по умолчанию не должны публиковаться наружу.

Основной способ доступа к ним:

- VS Code Remote SSH port forwarding

Важно:

- Docker может публиковать порты в обход `ufw`
- проект не должен отдельно усложняться ради решения этой проблемы
- это принимается как известный компромисс простого проекта

## Docker

Docker нужен для:

- Dev Containers
- обычных контейнерных задач на сервере

Требования:

- установить Docker по официальной документации Docker для Ubuntu
- обеспечить наличие `docker compose`
- добавить `dev` в группу `docker`
- не настраивать rootless Docker
- не добавлять автоматическую очистку Docker-мусора

## OpenCode

OpenCode входит в основной scope проекта.

Требования:

- OpenCode устанавливается нативно на хост
- OpenCode запускается как `systemd` service
- используется именно `opencode web`
- сервис стартует автоматически после перезагрузки
- OpenCode доступен через `Caddy` по HTTPS на `opencode.example.com`
- аутентификация делается только средствами самого OpenCode
- для OpenCode должен быть задан `OPENCODE_SERVER_PASSWORD`

Не нужно добавлять дополнительную auth-прослойку в `Caddy`.

Внутренние настройки OpenCode, модели, провайдеры и пользовательские предпочтения не входят в scope проекта.

## Caddy

Caddy нужен только как простой reverse proxy перед OpenCode.

Требования:

- Caddy завершает TLS
- Caddy проксирует OpenCode
- HTTPS поднимается автоматически стандартным способом Caddy

Предположение:

- DNS для `opencode.example.com` уже указывает на VPS к моменту web/setup-этапа

Не нужно тянуть wildcard-сертификаты, DNS API и другие усложнения.

## Packages and Host Setup

На хосте нужен только обязательный минимум.

Достаточно ориентироваться на такой набор:

- `git`
- `curl`
- `tmux`
- `ufw`
- `ca-certificates`
- Docker
- Caddy

Можно поставить ещё что-то небольшое, если это реально нужно реализации, но проект не должен превращаться в набор личных dotfiles и developer tooling.

## User Environment

Требования:

- оставить `bash`
- не настраивать `zsh`
- не раскладывать dotfiles
- не настраивать `nvim`, `tmux.conf` и другие личные пользовательские конфиги
- создать `/home/dev/projects` как рекомендуемый каталог для проектов

При этом VS Code и OpenCode не должны быть искусственно ограничены только этой директорией.

## Host Defaults

Нужны только простые системные значения:

- timezone: `Europe/Moscow`
- swapfile: `2 GB`

Этого достаточно.

## Secrets and Config

Конфиг должен оставаться простым и близким к обычному Ansible.

Нужно разделить:

- адрес хоста и connection settings
- обычные переменные
- секреты

Секреты должны храниться через `ansible-vault`.

Минимально ожидаемые секреты:

- пароль `root` для первого подключения
- пароль `dev` для `sudo`
- пароль OpenCode

Точная структура файлов может быть простой и удобной. Не нужно раздувать репозиторий ради “правильной” архитектуры.

## Repository Shape

Репозиторий должен оставаться маленьким и очевидным.

Ожидаемо, что в нём будут:

- `README.md`
- inventory
- vars
- vault secrets
- один или несколько playbook-ов
- шаблоны для конфигов, если они нужны

Не нужно тащить сложную role-архитектуру, CI, Molecule и прочую тяжёлую обвязку.

## Validation

Проверки должны быть только самые полезные и простые.

Достаточно проверять:

- что используется поддерживаемая ОС
- что заданы обязательные переменные и секреты
- что OpenCode после настройки не открыт без пароля
- что публичный HTTPS endpoint OpenCode в итоге отвечает

Проверка HTTPS может требовать небольшой retry после запуска `Caddy`, это нормально.

Не нужно строить сложную preflight-систему.

## Documentation

`README.md` должен быть коротким и практичным.

В нём достаточно описать:

- что делает проект
- какие есть допущения
- какие переменные и секреты надо заполнить
- какие команды запускать
- в каком порядке запускать playbook-и
- какой результат должен получиться

Не нужно превращать README в большую операционную документацию.

## Success Criteria

Проект считается успешным, если:

1. Новый Ubuntu 24.04 VPS можно настроить этим проектом без ручной системной донастройки.
2. После bootstrap можно зайти по SSH как `dev` по ключу.
3. `dev` может использовать `sudo`.
4. Docker работает для remote development сценариев.
5. OpenCode автоматически запускается после перезагрузки.
6. `https://opencode.example.com` открывает OpenCode через `Caddy`.
7. Репозиторий остаётся достаточно простым, чтобы его можно было понять без опыта в Ops.

## Deferred

Не входят в текущую версию:

- внешняя авторизация через Google или другую SSO-схему
- публикация временных dev preview наружу
- wildcard DNS/TLS automation
- мониторинг и графики
- продвинутый hardening
- бэкапы на уровне проекта
- CI/lint/test infrastructure
- сложная role-based архитектура
