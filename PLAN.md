# PLAN

## Что найдено в репозитории

Сейчас в репозитории есть только `SPEC.md`. Значит, проект разумно собирать с нуля и не вводить лишнюю архитектуру.

Ограничение на реализацию:

- в процессе реализации ничего не запускать
- все проверки ниже описаны как список того, что нужно будет проверить позже, отдельно от этапа написания файлов

## Минимальная структура файлов

Предлагаемая структура:

- `README.md` — короткая инструкция по заполнению переменных и запуску playbook-ов
- `ansible.cfg` — минимальные настройки Ansible для локального запуска проекта
- `inventory/hosts.yml` — один хост и connection settings
- `group_vars/all.yml` — обычные переменные проекта
- `group_vars/all/vault.yml` — секреты в `ansible-vault`
- `bootstrap.yml` — первый этап: подготовка доступа через `dev`
- `site.yml` — второй этап: базовая настройка хоста, Docker, Caddy, OpenCode
- `templates/sshd_config.d/99-bootstrap.conf.j2` — настройки SSH после bootstrap
- `templates/Caddyfile.j2` — reverse proxy для OpenCode
- `templates/opencode.service.j2` — `systemd` unit для `opencode web`

Почему так:

- достаточно двух playbook-ов, как требует SPEC
- без `roles/`, потому что для одного VPS это лишнее
- шаблоны только там, где реально нужны конфиги

## Этапы реализации

### Этап 1. Подготовить каркас репозитория

Цель:

Создать минимальный Ansible-скелет, чтобы дальше добавлять логику без перестройки структуры.

Файлы:

- создать `README.md`
- создать `ansible.cfg`
- создать `inventory/hosts.yml`
- создать `group_vars/all.yml`
- создать `group_vars/all/vault.yml`
- создать `bootstrap.yml`
- создать `site.yml`
- создать `templates/sshd_config.d/99-bootstrap.conf.j2`
- создать `templates/Caddyfile.j2`
- создать `templates/opencode.service.j2`

Что потом проверить:

- структура файлов соответствует плану
- `ansible-inventory -i inventory/hosts.yml --list` отрабатывает без ошибок структуры
- `ansible-playbook --syntax-check bootstrap.yml`
- `ansible-playbook --syntax-check site.yml`

### Этап 2. Описать переменные и секреты

Цель:

Отделить connection settings, обычные переменные и секреты, но не усложнять модель данных.

Файлы:

- изменить `inventory/hosts.yml`
- изменить `group_vars/all.yml`
- изменить `group_vars/all/vault.yml`
- изменить `README.md`

Что должно быть описано:

- адрес VPS, `ansible_user`, способ подключения на bootstrap и после него
- домен OpenCode
- публичный SSH-ключ для `dev`
- timezone, swap size, путь `/home/dev/projects`
- секреты: пароль `root`, пароль `dev`, `OPENCODE_SERVER_PASSWORD`

Что потом проверить:

- обязательные переменные и секреты явно перечислены в документации
- `ansible-vault edit/view group_vars/all/vault.yml` подходит для хранения секретов
- playbook-и смогут ссылаться на переменные без дублирования

### Этап 3. Реализовать bootstrap-доступ

Цель:

С первого входа под `root` подготовить нормальную дальнейшую работу через пользователя `dev`.

Файлы:

- изменить `bootstrap.yml`
- изменить `templates/sshd_config.d/99-bootstrap.conf.j2`
- при необходимости изменить `group_vars/all.yml`
- при необходимости изменить `group_vars/all/vault.yml`

Что должно делать:

- проверить, что целевая ОС — Ubuntu 24.04
- установить минимум пакетов, нужных уже на bootstrap-этапе
- создать пользователя `dev`
- задать ему пароль из vault
- добавить `dev` в группу sudo
- установить SSH-ключ для `dev`
- создать `/home/dev/projects`
- отключить SSH password auth
- отключить прямой SSH login под `root`

Что потом проверить:

- `ansible-playbook bootstrap.yml` выполняется на чистом VPS
- после выполнения можно войти как `dev` по ключу
- вход по SSH под `root` запрещён
- вход по паролю по SSH запрещён
- `dev` может выполнить `sudo` с паролем
- повторный запуск `bootstrap.yml` не должен ломать систему

### Этап 4. Добавить базовую системную настройку

Цель:

Оставить только обязательный минимум хост-настроек из SPEC.

Файлы:

- изменить `site.yml`
- при необходимости изменить `group_vars/all.yml`
- изменить `README.md`

Что должно делать:

- проверить обязательные переменные до основной настройки
- установить timezone `Europe/Moscow`
- создать swapfile `2 GB`
- установить базовые пакеты: `git`, `curl`, `tmux`, `ufw`, `ca-certificates`
- настроить firewall только на `22/tcp`, `80/tcp`, `443/tcp`

Что потом проверить:

- timezone применён корректно
- swapfile существует и активен
- нужные пакеты установлены
- `ufw status` показывает только требуемые правила
- повторный запуск `site.yml` остаётся идемпотентным

### Этап 5. Установить Docker

Цель:

Обеспечить Docker для Dev Containers и обычных контейнерных задач без дополнительной сложности.

Файлы:

- изменить `site.yml`
- при необходимости изменить `README.md`

Что должно делать:

- подключить официальный Docker repository для Ubuntu
- установить Docker Engine и `docker compose`
- включить и запустить Docker service
- добавить `dev` в группу `docker`

Что потом проверить:

- `docker --version` доступен на хосте
- `docker compose version` доступен на хосте
- `systemctl status docker` показывает активный сервис
- пользователь `dev` может работать с Docker после нового входа в сессию

### Этап 6. Установить и запустить OpenCode через systemd

Цель:

Поднять OpenCode нативно на хосте, без лишних слоёв.

Файлы:

- изменить `site.yml`
- изменить `templates/opencode.service.j2`
- при необходимости изменить `group_vars/all.yml`
- при необходимости изменить `group_vars/all/vault.yml`

Что должно делать:

- установить OpenCode на хост
- настроить запуск именно через `opencode web`
- передать `OPENCODE_SERVER_PASSWORD`
- создать и включить `systemd` unit
- убедиться, что сервис стартует после перезагрузки

Что потом проверить:

- `systemctl status` для сервиса OpenCode показывает `active`
- сервис слушает локальный порт, который будет проксировать Caddy
- OpenCode не доступен без пароля
- после `reboot` сервис поднимается автоматически

### Этап 7. Настроить Caddy как HTTPS reverse proxy

Цель:

Сделать самый простой публичный HTTPS-доступ к OpenCode.

Файлы:

- изменить `site.yml`
- изменить `templates/Caddyfile.j2`
- при необходимости изменить `group_vars/all.yml`

Что должно делать:

- установить Caddy
- настроить reverse proxy на локальный OpenCode endpoint
- включить и запустить Caddy
- оставить аутентификацию только на стороне OpenCode

Что потом проверить:

- DNS домена уже указывает на VPS
- `systemctl status caddy` показывает `active`
- HTTPS endpoint `https://opencode.example.com` отвечает
- при первом старте допускается retry, пока Caddy получает сертификат
- публичный endpoint не открывает OpenCode без пароля

### Этап 8. Добавить минимальные проверки в playbook-и

Цель:

Покрыть только те валидации, которые прямо требуются в SPEC.

Файлы:

- изменить `bootstrap.yml`
- изменить `site.yml`

Что должно быть проверено:

- поддерживаемая ОС
- наличие обязательных переменных
- наличие обязательных секретов
- OpenCode не открыт без пароля
- HTTPS endpoint отвечает после настройки

Что потом проверить:

- при пропуске обязательной переменной playbook падает с понятной ошибкой
- при неподдерживаемой ОС playbook завершается сразу
- финальная HTTP/HTTPS-проверка действительно ловит неверную конфигурацию

### Этап 9. Сократить и вычистить документацию

Цель:

Оставить README коротким и практичным, без ops-обвязки.

Файлы:

- изменить `README.md`

Что должно быть в README:

- назначение проекта
- допущения
- какие переменные и секреты заполнить
- какие команды запускать
- порядок запуска: сначала `bootstrap.yml`, потом `site.yml`
- ожидаемый результат после завершения

Что потом проверить:

- README можно пройти сверху вниз без дополнительных пояснений
- в README нет лишней архитектурной или операционной документации
- новый пользователь может понять порядок запуска без чтения исходников

## Итоговая последовательность работ

1. Создать минимальный каркас файлов.
2. Описать inventory, обычные переменные и vault secrets.
3. Реализовать `bootstrap.yml` для перехода с `root` на `dev`.
4. Реализовать `site.yml` для базовой настройки хоста.
5. Добавить Docker.
6. Добавить OpenCode как `systemd` service.
7. Добавить Caddy с HTTPS reverse proxy.
8. Встроить минимальные проверки.
9. Сжать README до практической инструкции.

## Что сознательно не делать

- не добавлять `roles/`
- не добавлять CI, Molecule, test framework
- не добавлять сложный preflight
- не добавлять отдельный playbook для каждого маленького шага
- не добавлять dotfiles и пользовательскую кастомизацию
- не добавлять продвинутый hardening сверх требований SPEC
